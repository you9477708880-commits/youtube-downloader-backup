## 三、必做修正與驗收條件

以下位置是檢查入口，行號可能隨修改變動。先重現並補有意義的回歸測試，再修正；若現行程式已修好，提供證據，不重複修改。

### A. JSON 還原的本機保存邊界

入口：`src/app/controllers/import-controller.js` 的 `importBackupFile`、`src/app/controller-lifecycle.js`。

先前流程先 replaceWholeState，再 persistWholeState；保存失敗可能留下「畫面／記憶體已換資料，本機實際沒存好」的狀態。

- 先解析、驗證、正規化候選資料，再成功保存至正確本機 namespace，才替換 store、重設 controller、更新 UI、安排同步。
- 讀檔、驗證或本機保存失敗時，原本 store、持久化資料與編輯草稿不應遭到提前替換；不可顯示成功。
- 檢查非同步讀檔期間切換 UID／登入狀態的情境，禁止把舊操作結果套用到新使用者。沿用既有 scope／generation 設計，不另造同步架構。
- 保留既有衝突復原與還原確認，不重新引入每次自動下載 JSON 的行為。
- 不承諾跨多個 storage key 的原子性；若現行實作需要多鍵寫入，必須測試部分失敗與可恢復性，不能只交換兩行呼叫就宣稱安全。

### B. 匯入資料與同步識別碼一致

入口：`src/services/import-export.js`、`src/services/record-codec.js`。

先前 shape 驗證可接受重複 ID，同步 codec 卻拒絕同一組資料。

- 對同步 codec 涉及的集合，使用一致的 canonical ID 與集合／kind 邊界檢查重複；包含數字 `1` 與字串 `"1"` 的碰撞，不把合法跨集合 ID 視為重複。
- 匯入前以既有匯入介面顯示可理解的錯誤摘要與項目位置；不另做健康檢查儀表板，不在 log 輸出整份私人帳務。
- 不合法備份整份拒絕，零寫入；不得偷偷刪重複、替既有資料換 ID、破壞準備金或還款關聯。
- 正常舊版備份、現有 schema 與 CSV 帳戶修復／重複辨識流程保持相容。CSV 的重複列處理不可被誤改成 JSON 的拒絕規則。

### C. 畫面更新失敗不能截斷同步處理

入口：`src/app/state-commit.js` 與相關 coordinator。

先前 updateUi 拋例外後，enqueueCloud 不會被呼叫。

- 維持「normalize → 本機成功保存 → store 更新」的耐久性邊界。本機保存失敗，不得排入雲端或呈現已完成。
- 本機已保存、UI 更新失敗時，仍須安排同一次有效 scope 的已提交 snapshot 同步，或進入既有可重試的待同步狀態；不得無條件抓取另一使用者／另一筆更新後的 state。
- 清楚區分「本機未保存」「本機已保存但畫面更新失敗」「等待／無法雲端同步」，不可把 UI 失敗說成資料完全沒存，也不可顯示雲端成功。
- 覆蓋 UI 例外、enqueue 例外／非同步失敗、重入更新與 scope 切換。避免使用會吞掉原始錯誤或重複保存的泛用 finally。
- 不重新設計 record-level sync、revision、outbox、tombstone 或自動合併。

### D. 刪除正在編輯的交易

入口：`src/app/controllers/transaction-controller.js`、`src/domain/transaction-commands.js`。

先前「編輯 → 刪除 → 儲存」會因 editing target 已不存在而建立新 ID 的交易。

- 刪除目前編輯對象後清除對應編輯狀態；不清除其他無關草稿。
- domain 收到不存在的 editing ID 必須回報明確失敗，不回退成新增。
- 包含關聯刪除／遠端資料替換造成對象消失的情境，不復活 tombstone，不破壞代墊／還款 cascade。

### E. 信用卡日期顯示

入口：`src/domain/account-center.js`、`src/views/balance-sheet-view.js` 與帳戶編輯 controller。

- 空白、0、未設定不得被 clamp 成每月 1 日；顯示「未設定」，不虛構日期。
- 「最近預定繳款日」定義為今天或之後最近一次依設定推算的日期；「下一期帳單繳款日」如保留，須另外命名，不能混為同一數字。
- 例：2026-09-20、結帳日 5 日、繳款日 23 日，最近預定繳款日是 2026-09-23，而非直接跳到 10 月。
- 同一天視為今天到期，不因時分秒提早跳下月；測跨月、跨年、僅設定部分日期與既有允許日期範圍。
- 不推測銀行實際帳單、已繳清與否、假日順延或銀行營業日；簡短標示為依設定推算。沒有實際帳單資料時，不聲稱仍欠款。
- 不加入銀行串接、自動付款、利息計算或新持久化欄位。

### F. 生活提醒的「查看紀錄」

入口：`src/app/controllers/life-record-reminder-controller.js` 與交易搜尋 controller。

- 提醒依歷史紀錄計算；點「查看紀錄」必須能看到對應歷史交易，不能被搜尋預設最近半年隱藏。
- 使用既有搜尋入口，設定合適期間（例如全部期間），清楚顯示期間；不改總覽／月度報表日期，不新增第二套清單。
- 覆蓋超過半年、無符合紀錄與切換不同提醒；不新增背景通知或其他提醒設定。

## 四、唯一新增功能：從這筆再記一筆

讓常見午餐、加油等支出少打幾次字，不新增模板管理區。

- 在既有交易詳情提供「再記一筆」，沿用既有新增表單；初版僅開放無特殊關聯的一般收入／支出。
- 預填金額、分類、子分類、備註及有效帳戶；日期預設今天，可再修改。明確顯示是在新增，不是編輯原紀錄。
- 使用者確認儲存才建立新交易與新 ID；關閉／取消不寫入。原紀錄不變，連續點擊不得造成非預期重複送出。
- 不複製匯入 external identity、同步 metadata、準備金、代墊、還款等關聯。不支援轉帳、對帳調整、還款、代墊或含特殊關聯交易的複製；入口隱藏或明確說明不可用。
- 已有未保存草稿時先詢問是否放棄；已刪除／停用的帳戶或分類依現行規則要求重選，不默默指向其他帳戶。
- 不持久化模板、不加入週期自動記帳、不改 CSV 去重邏輯。

## 五、測試、審核與停止條件

先針對 A～F 與再記一筆補 domain／controller／service 回歸測試，再做整合檢查。至少驗證：

| 範圍 | 必要證據 |
| --- | --- |
| JSON 還原 | 成功、解析失敗、重複 canonical ID、quota 失敗、讀檔期間 UID 切換，確認零誤寫 |
| commitState | 本機保存失敗、UI 失敗、雲端排隊失敗的狀態與實際呼叫順序 |
| 編輯刪除 | 編輯後刪除再儲存不重建；不存在的 editing ID 明確拒絕 |
| 信用卡 | 未設定、今天到期、跨月／年、最近繳款日與下期帳單日的差異 |
| 提醒 | 一年前的紀錄可從提醒找到，月度報表範圍不變 |
| 再記一筆 | 草稿保護、取消零寫入、儲存只有一筆新交易、原 ID／匯入身份不沿用 |
| 既有資料操作 | 合成 450 筆 CSV 重複匯入與帳戶修復；準備金／代墊／還款回歸 |
| UI | 桌面與手機尺寸；詳情、長備註、按鈕及鍵盤焦點無回歸；既有分頁不丟失 |

使用合成 fixtures，不要求讀取使用者真實 450 筆財務資料。異常注入限一般儲存／UI／queue 錯誤，不涉及漏洞利用測試。

本批完整本機驗證按 `package.json` 現行定義執行：`check:env`、`test:unit`、`test:release`、`test:acceptance`、`test:emulators`、`test:smoke`。可分項執行以確保某項失敗後，其他項目仍取得結果；`npm test` 是完整入口，不把 `test:fast` 稱為完整 CI。

- 開始時查 Node `24.15.0`、Java 21、專案內 firebase-tools `15.22.4` 與實際環境是否相符；Functions runtime 20 是獨立雲端目標，不需把本機降至 Node 20。
- 不同測試會使用共同打包輸出目錄，依現有 runner 避免互相覆寫；不要外層盲目平行執行全部套件。
- Emulators 僅使用 demo 專案。若仍遇已知 Windows Rules 管理端點 503，保存一次受控嘗試的紀錄、完成不受影響測試，標記「本機環境阻塞，待另授權推送後固定 Ubuntu CI 驗證」。不反覆重裝 Java、不升級依賴、不將歷史 CI 通過當成本批通過。
- 非既知 503 的新錯誤不得直接歸類環境問題，須先診斷；若觸及新授權才停止該項。
- 最後修改後重新跑受影響測試，完整套件有有效的同版證據；保留失敗與重跑結果，不只留下最後綠燈。
- 安排至少一個未參與實作的獨立子代理審核最終 diff，重點看保存邊界、ID、UID、刪除語意；另一個可檢查日常操作。子代理只審核，不同時改同一檔案。
- 審核有問題則修正、重測，再請複核；無重大發現不代表百分之百安全。

若必須變更 schema／migration／Rules／Functions、安裝依賴、改帳務定義、存取正式資料或推送才能繼續，停止該部分並提出具體選項；其他不受影響項目仍完成。不得擴大為整套同步重寫或以行數為理由繼續切分。

退休重算效能、全站索引、資產配置新功能等留待後續，不納入本批。

## 七、模型建議

本批建議主執行模型使用 GPT-6 Astra，推理程度 XHigh；獨立審核同模型 High 或 XHigh。若重視速度，可用 High 完成整批。無需預設全部開 Max／Ultra；高推理不代替故障注入、測試或獨立審核。

這是依跨模組保存、匯入識別碼與狀態切換風險做的工程建議，不是品質保證。實際選項以新對話的模型選單為準。2026-09-20 查核的 [OpenAI 官方模型指南](https://developers.openai.com/api/docs/guides/latest-model) 將 GPT-6 Astra 定位於軟體工程與多步工作流程；XHigh 的選擇是本批建議，並非該頁對本專案的規定。
