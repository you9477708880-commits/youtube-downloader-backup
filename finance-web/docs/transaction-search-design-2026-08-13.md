# 交易搜尋與生活事件回顧設計

日期：2026-08-13

## 1. 使用者問題

記帳內容不只用於統計，也會成為生活日記。例如搜尋「洗牙」或「保養車」，確認最近一次與歷次紀錄，判斷距離上次多久。

目前網站只有日期區間篩選，沒有關鍵字搜尋；而且日期控制位於總覽頁，在記帳頁不容易被發現。因此只在現有 selector 加一個文字條件並不足以解決使用問題。

## 2. 候選方案

### 方案一：記帳頁內的交易搜尋（建議先做）

在記帳列表上方加入搜尋區，包含關鍵字、常用期間及結果摘要。搜尋結果仍使用既有交易列，因此可查看、修改或刪除原交易。

優點：符合使用路徑、無需新資料格式、可直接支援 AndroMoney 匯入紀錄。缺點：只找得到使用者曾經寫進交易的內容。

### 方案二：全站頂部搜尋

從所有頁面搜尋交易、準備金、願望與資產負債。

優點：入口固定。缺點：不同資料的刪除、金額與日期語意不同；第一版容易產生混雜且難解釋的結果。

### 方案三：生活事件／保養追蹤中心

讓使用者建立「洗牙每 6 個月」「汽車每 5,000 公里」等追蹤項目，並連結相關交易。

優點：能真正提醒下一次。缺點：需要新增持久化資料、migration、同步、匯入匯出與刪除語意；里程型週期也不是單靠日期可解決。

## 3. 建議產品路徑

先實作方案一，稱為「搜尋紀錄」。它能立即解決回查日記的需求，且不改 schema。實際使用一段時間後，再根據常搜關鍵字判斷是否值得進入方案三。

第一版應包含：

- 搜尋入口放在記帳頁右側列表上方；手機版位於交易列表標題下方。
- 關鍵字搜尋範圍：備註 `desc`、主分類、子分類、代墊對象、帳戶名稱及關聯準備金名稱。
- 預設期間「近 6 個月」，另提供近 1 年、全部與自訂日期。
- 搜尋採不分英文大小寫的包含比對；多個空白分隔詞採「全部都要符合」。中文不依賴斷詞服務。
- 顯示命中筆數、最近一次日期、距今天數；有至少兩筆時顯示最近兩次間隔。
- 顯示「這是記帳紀錄，不代表醫療或保養建議」，不自動推算下一次日期。
- 清除搜尋後恢復原本記帳列表；搜尋字與專用期間皆為 UI 狀態，不寫 localStorage 或 Firestore。

### 搜尋例子

- `洗牙`：命中備註「例行洗牙」。
- `汽車 保養`：同一筆資料的可搜尋文字必須同時包含「汽車」與「保養」。
- `醫療 洗牙`：可由主分類「醫療」加備註「洗牙」共同命中。

## 4. 與既有日期篩選的邊界

搜尋使用自己的期間，不直接改動總覽的報表日期。原因是使用者可能正在看本月預算，卻想搜尋過去半年；搜尋不應讓總覽、月度回顧與目標中心一起跳到半年區間。

記帳頁未輸入關鍵字時仍沿用目前全站報表日期；輸入第一個關鍵字時，搜尋期間預設近 6 個月。畫面需明確標示「搜尋期間」，避免兩套日期造成誤解。

## 5. 技術設計（階段 A，不改 schema）

新增純函式：

```js
searchTransactions({ transactions, accounts, funds, query, range, today }) => {
  matches,
  matchCount,
  latestDate,
  daysSinceLatest,
  latestIntervalDays
}
```

建議檔案邊界：

- `src/domain/transaction-search.js`：文字正規化、欄位投影、日期篩選、命中與間隔摘要。
- `src/views/transaction-search-view.js`：搜尋控制與摘要，輸出一份 search criteria。
- `src/app/search-controller.js` 或 bootstrap 內的小型 UI coordinator：持有暫時 query/range，呼叫 domain 後將 `matches` 傳給既有 `renderLedger()`。
- `index.html`、局部 CSS、`event-bindings.js`：搜尋輸入與清除事件。
- 新增 domain、view、event 與 smoke tests。

不修改：initial state、normalize、schemaVersion、JSON validator、record codec、Firestore Rules、Functions、AndroMoney CSV 欄位。

## 6. 資料與帳務安全

- 搜尋只選取既有 `txs`，不建立交易、不改金額、不重算帳務。
- income、expense、transfer、advance、advance_repayment 都可搜尋；結果保持原類型及原操作。
- 搜尋摘要只計算「紀錄出現時間」，不把金額加總成新的財務指標，避免代墊或轉帳語意誤用。
- AndroMoney 匯入的 `category`、`subcategory`、`desc` 可直接被搜尋；`externalId`、UID 等內部來源欄位不納入一般搜尋。
- 使用者文字輸出 HTML 前必須 escape；正規化不可回寫 transaction。
- UID 或整份 state 切換時清除搜尋條件，避免上一個帳號的關鍵字或結果殘留在畫面。

## 7. 測試與風險

必測：

- 中文、英文大小寫、全形／半形（Unicode NFKC）與前後空白。
- 多詞 AND、分類＋備註跨欄位命中、帳戶與準備金名稱命中。
- 日期起訖邊界、閏日、無效日期及 `today` 固定注入。
- 0、1、2 筆以上結果的最近日期與間隔摘要。
- transfer 的兩個帳戶、advance 的 person、repayment 的原始描述。
- 搜尋不改 state、不 commit、不 enqueue cloud。
- 惡意 HTML 字串不可被執行。
- 搜尋中編輯／刪除後立即重跑結果，不保留已不存在的 transaction。
- UID／JSON replacement 後搜尋重設。
- 桌面與 390px 手機版無水平溢出；清除搜尋可還原列表。

效能方面，個人記帳即使有數萬筆，先在前端建立小寫搜尋文字後線性掃描通常足夠。輸入事件應使用約 150–250ms debounce；若實測資料量造成卡頓，再考慮快取索引，不先加入搜尋依賴。

## 8. 階段 B（需另行授權）

若未來要提供「下次洗牙」或「下次保養」提醒，建議新增獨立 `routines`／`lifeTrackers` 集合，而不是把提醒欄位塞進每筆交易。它需要定義：週期單位、手動確認、交易連結、延後、完成、刪除、跨裝置同步與匯入匯出。這會改正式資料格式，必須另外設計 migration 與 Emulator 測試。

## 9. 階段 A 驗收條件

- 使用者可在記帳頁以「洗牙」搜尋近 6 個月，看到所有命中交易與最近一次摘要。
- 改成近 1 年、全部或自訂日期時結果正確。
- 搜尋可跨備註、分類、子分類、代墊對象、帳戶及準備金名稱。
- 搜尋不影響總覽目前選定的報表期間，也不保存或同步搜尋字。
- 命中交易仍可使用原本的修改、刪除及準備金查看操作。
- 全部既有帳務、同步、匯入、Emulator 與 smoke 測試保持通過。
